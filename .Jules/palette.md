# Palette Journal — sub12

## 2026-05-27 - Comment input: placeholder ≠ label, silent maxLength is invisible
**Learning:** This codebase has excellent ARIA hygiene on buttons (aria-label on every icon-only button, aria-pressed, aria-expanded, aria-haspopup) but the inline comment `<input>` inside `PostCard` relied solely on `placeholder` — no `aria-label`. The pattern recurs wherever a text input appears *inside a form that already has a labelled submit button*; devs may assume the button context implies the input's purpose, but screen readers don't share that assumption. Also: `maxLength` on an input is completely invisible to users — the browser just silently stops accepting characters. Always pair `maxLength` with a visible counter (show when < 80 remaining, turn red at < 10).
**Action:** When reviewing inline comment/reply boxes in this app, check for (1) `aria-label` on the `<input>`, and (2) a visible `"{n} remaining"` counter linked via `aria-describedby` + `aria-live="polite"`.

## 2026-05-27 - CatalogSearch: custom comboboxes need explicit ARIA even when keyboard-navigable
**Learning:** `CatalogSearch` (used in the pellet and rifle wizards) had working keyboard navigation (arrow keys, Enter, Escape) but was completely silent for screen readers. The component had no `role="combobox"`, no `aria-expanded`, no `role="listbox"` on the dropdown, and no `role="option"` on suggestions. Crucially, the accessible name of the input was only the `placeholder`, which vanishes the moment typing begins — so the input became a completely anonymous text field mid-session. The fix combined `type="search"` + `aria-label={placeholder}` + full combobox ARIA (role, aria-expanded, aria-controls, aria-haspopup, aria-autocomplete) + `role="listbox"` + `role="option"` / `aria-selected` on each item. React 18's `useId()` pairs the input to its listbox id reliably even when multiple CatalogSearch instances are mounted simultaneously.
**Action:** When reviewing wizard steps in this app, check every custom dropdown/autocomplete for: (1) `role="combobox"` + `aria-expanded` + `aria-haspopup="listbox"` on the input, (2) `aria-label` (not just placeholder) on the input, (3) `role="listbox"` on the container, (4) `role="option"` + `aria-selected` on each item. Visual keyboard navigation alone is not sufficient ARIA coverage.

## 2026-07-02 - Native `confirm()`/`window.confirm()` still lingers on several destructive actions despite ConfirmDialog being the established pattern
**Learning:** Most delete/destroy flows already use the branded `ConfirmDialog` component (20 pages import it), but a handful of pages still call the native `confirm()`/`window.confirm()` browser dialog directly for destructive actions: `pages/Locations.tsx` (delete location — fixed this session), `pages/AdminEvents.tsx` (delete event, remove category — 2 call sites), `pages/AdminBackup.tsx` (restore backup, delete backup, restore from upload — 3 call sites). These render as unbranded, unstyled browser popups that break visual consistency and (per the two entries above) generally correlate with weaker ARIA/focus handling than the app's own components. `grep -rn "confirm(" frontend/src/pages` is the fast way to re-find these; watch for false positives like `communityReviewApi.confirm(...)` / `confirmMutation` which are unrelated review-confirmation API calls, not the browser dialog.
**Action:** The `AdminEvents.tsx` and `AdminBackup.tsx` call sites are still open — worth converting in a future session (each needs a `deleteTarget`/`actionTarget`-style state var like the `Locations.tsx` fix, since `ConfirmDialog` is stateful/controlled rather than a promise-based `confirm()` drop-in).

## 2026-07-10 - AdminEvents.tsx converted to ConfirmDialog; AdminBackup.tsx still open
**Learning:** Converted the 2 remaining native `confirm()` sites in `pages/AdminEvents.tsx` (delete event, remove category) to the branded `ConfirmDialog`. Both destructive mutations already exposed `onSettled`/`onSuccess`, so the state-clearing (`setDeleteTarget(null)` / `setRemoveTarget(null)`) was safest wired through `onSettled` on the mutation itself rather than in the dialog's `onConfirm` callback — that way the dialog also closes correctly if the mutation errors, not just on success.
**Action:** `pages/AdminBackup.tsx` (restore backup, delete backup, restore from upload — 3 call sites) is the last file with native `confirm()`/`window.confirm()` in `pages/`. Worth converting in a future session using the same `actionTarget`-style state pattern; re-check with `grep -rn "confirm(" frontend/src/pages` (watch for `communityReviewApi.confirm(...)` / `confirmMutation` false positives).
