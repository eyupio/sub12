## 2026-08-06 - Uncapped Free-Text Profile Fields (Storage/Bandwidth DoS)
**Vulnerability:** `UserService.UpdateMe` (`backend/internal/service/user.go`) validated `DisplayName` length (64) but let `Bio`, `Location`, and `Club` through untouched. Handler-side there was no per-field check either — only the 1 MiB JSON body cap. An authenticated user could `PATCH /api/v1/users/me` with a ~1 MiB `bio` (or split across the three) and have it persisted in the `TEXT` columns of `users`; every subsequent profile view (`GET /api/v1/users/{id}`, `PublicProfile` in feed/comment/scorecard payloads) then re-served the blob to every viewer. Same shape as the device-token entry below.
**Learning:** The same lesson from the device-token, uncapped-limit, and unbounded-JSON entries. Every free-form string that reaches a DB column needs its own service-layer cap. `TEXT` in Postgres is unlimited and doesn't push back. Runes not bytes so a Japanese/Arabic bio isn't punished vs an ASCII one.
**Prevention:** Grep `*string.*json:"` in `backend/internal/model/*.go` and cross-check each corresponding `service.UpdateX` for a `len([]rune(*in.Field)) > cap` guard. Caps (`maxUserBioLen = 1000`, `maxUserLocationLen = maxUserClubLen = 120`) sit next to `emailChangeTTL` with a comment naming the DoS shape. New regression test: `TestUserService_UpdateMe_FreeTextLengthCaps` runs one case per field with `NewUserService(nil, nil, nil, ...)` — validation refuses before the nil repo is touched.

## 2026-07-30 - Login User-Enumeration via bcrypt Timing Side Channel
**Vulnerability:** `AuthService.Login` (`backend/internal/service/auth.go:126`) short-circuited on `ErrNotFound` and on `user.PasswordHash == nil` (OAuth-only accounts) *before* running `bcrypt.CompareHashAndPassword`. Because bcrypt at `DefaultCost` takes ~50–200ms depending on cost, an unauthenticated attacker could measure `POST /auth/login` latency: a fast reject means the email is unregistered (or OAuth-only), a slow reject means the account exists with a password. The login rate limit slows a scan but doesn't hide the per-request timing signal; the 2FA challenge issuance path was even more distinguishable because it did further crypto only when the account existed AND the password matched. Combined with the previously-fixed generic-error responses (which do the right thing on the *body*), the timing signal was the only remaining enumeration vector on this endpoint.
**Learning:** Generic error strings are necessary but not sufficient for enumeration defence — any code path that runs the same code on both branches is fine, but the moment one branch skips an expensive crypto step the enumeration is back. The classic fix is a package-level "dummy" bcrypt hash of an unknowable value (32 bytes from `crypto/rand`, discarded after hashing) that the not-found and no-password branches run bcrypt against and discard the result. Cost must match `bcrypt.DefaultCost` — if it drifted the timing signal would reopen — so pin it with a `bcrypt.Cost(dummyBcryptHash) == bcrypt.DefaultCost` test. `RequestPasswordReset` deliberately returns `nil` on `ErrNotFound` for the same enumeration reason, but it doesn't run bcrypt either — the fast path there is one DB lookup regardless, so timing is much closer.
**Prevention:** Any authentication code path that runs bcrypt (or any comparable-cost primitive) on the "credentials valid" branch must run it on the "user not found" and "credential shape mismatch" branches too. Grep for `bcrypt\.CompareHashAndPassword` and confirm each caller has a paired dummy-hash comparison on the negative path. Regression tests added: `TestDummyBcryptHash_MatchesDefaultCost` (cost stays pinned) and `TestDummyBcryptHash_NeverMatchesCommonPasswords` (dummy plaintext is not reachable).

## 2026-07-16 - Missing Length Cap on Device Push Tokens (Storage DoS)
**Vulnerability:** `DeviceService.Register` (backend/internal/service/device.go:35) trimmed and validated the `Token` field but did not cap its length. The handler above uses `decodeJSON` which caps the JSON body at 1 MiB, so an authenticated user could `POST /api/v1/devices` with a ~1 MiB token string per call and store it in `device_tokens`. Every `Upsert` on the same `(user_id, platform)` overwrites the previous row, but rotating platforms (`ios`/`android`/`web`) gives three multi-MiB rows per user without extra effort — and even a single user rotating tokens keeps re-inflating one row's payload. Realistic tokens are tiny (FCM ~163 chars, APNs 64 hex, Web Push endpoints usually <512 bytes), so a 4096-byte cap has no legitimate side effect and cheaply defends the `device_tokens` table from becoming a storage-DoS surface.
**Learning:** JSON body caps at the framework layer aren't enough on their own for fields that get persisted — the same lesson as the earlier "uncapped `?limit=`" and "unbounded `json.NewDecoder`" entries. Anywhere user-controlled bytes reach a DB column, the service layer needs its own per-field length check; the request-body cap only limits what the *server* holds in memory, not what it hands off to storage. The device service was the outlier: string fields on other services (`Username`, `NewPassword`, comment bodies, etc.) already validate max length in their `service.*` functions.
**Prevention:** Grep `s\.repo\..*Upsert\|s\.repo\..*Insert` in `backend/internal/service/*.go` and confirm every string field that becomes a DB column has an explicit `len(field) > cap` check before the write. The `maxDeviceTokenLen = 4096` constant here is the model — a small, named, commented cap right next to the sentinel errors it composes with. New regression tests: `TestDeviceService_Register_Validation` "token too long" case + the corresponding `Unregister` case both assert `ErrInvalidDeviceToken`.

## 2026-07-02 - Missing Authorization on AdminDelete for Support Tickets + Feature Requests
**Vulnerability:** `SupportTicketService.AdminDelete(ctx, id)` and `FeatureRequestService.AdminDelete(ctx, id)` did not check that the caller was an admin — they went straight to `s.repo.Delete(ctx, id)`. Both are registered in the *authenticated-only* route group in `router.go` (not the `RequireAdmin` group) because sibling routes in the same block (`AdminUpdate`, `AdminCreateFromTicket`) support scoped **league/club** admins as well as platform admins — so the middleware can't enforce the check, and each service must self-gate. Every other admin action in that block did self-gate; delete was the outlier for both domains. Any authenticated user could `DELETE /api/v1/admin/tickets/{id}` or `DELETE /api/v1/admin/feature-requests/{id}` and wipe any row.
**Learning:** When a route is admin-flavoured but the middleware only enforces authentication (because scoped admins have to reach it too), *every* handler in that block has to call the same `isAdminForScope`/`isAdminForTicket` check itself. The moment you write `func (s *X) AdminDelete(ctx, id) error { return s.repo.Delete(ctx, id) }` you've lost the check that the surrounding routes have. The AdminUpdate sibling right above already had the correct pattern — the delete just skipped it.
**Prevention:** For every `Admin*` service method registered outside a `RequireAdmin` group, grep for the sibling admin methods and confirm each calls `isAdminForScope`/`isAdminForTicket` before mutating. `grep -nE 'func \(.+\) Admin.+\(ctx' backend/internal/service/*.go` lists all candidates; any that reduce to `return s.repo.<Mutate>(ctx, id)` with no scope check is a regression. Also: whenever an admin route's handler doesn't extract `userID` from the request context, that's a smell — real admin gates need the actor's ID.

## 2026-06-18 - Uncapped ?limit= on Ten List Endpoints (incl. unauth public leaderboard)
**Vulnerability:** Ten list handlers across `backend/internal/api/handler/` (`notification.go`, `user.go`, `event_invitation.go`, `feature_request.go` ×2, `support_ticket.go` ×2, `report.go`, `pellet_testing.go` ×2) parsed `?limit=` inline with their own little block — accepting any positive int with no upper bound. The worst case was `pellet_testing.go` `PublicLeaderboard` because it's the only public, unauthenticated route in the group: `GET /api/v1/pellet-tests/public-leaderboard?limit=999999999` would stream the entire leaderboard table out of the database. The repo already exposed a tested `parsePagination(r, defaultLimit, maxLimit)` helper in `health.go:59` that was used by ~10 OTHER handlers correctly.
**Learning:** A canonical helper only reduces risk if the *only* path to read pagination params is through it. New code drifted to copy-pasting the inline pattern because each block was 4 lines and "looked obviously fine." The same lesson as the journal's earlier 2FA decodeJSON entry — a helper exists, but discipline is fragile and grep is your friend.
**Prevention:** Grep with `Get\(\"limit\"\)` in `backend/internal/api/handler/`. Every hit that isn't inside `parsePagination` is a regression candidate. The new `TestParsePagination_LimitClampAndOffset` table-test in `pagination_test.go` pins the helper's contract (limit clamps to maxLimit, offset >=0, non-numeric → defaults). Consider extending the CI vet step with a `go test`-style linter that flags `Get(\"limit\")` outside the helper.

## 2026-06-11 - Unbounded JSON Body Decode on 2FA Handlers
**Vulnerability:** `backend/internal/api/handler/two_factor.go` called `json.NewDecoder(r.Body).Decode(&body)` directly in three handlers (`EnrollConfirm`, `Disable`, `RegenerateBackupCodes`). The package already exposes `decodeJSON(r, v)` (in `health.go`) which wraps the body in `io.LimitReader(r.Body, 1<<20)`, but these handlers bypassed it. A streaming POST could exhaust memory on the host since `json.Decode` keeps growing internal buffers until EOF or top-level value parses.
**Learning:** The repo already enforces a body cap at the public-auth boundary (see `security(auth): cap public auth endpoint bodies at 1 MiB`), and the `decodeJSON` helper exists exactly for this purpose, but newer handlers reached for `encoding/json` directly because the `auth.go` body-cap was wired via a different helper. A single canonical decoder is only useful if it is the *only* path to read JSON.
**Prevention:** After any change in `backend/internal/api/handler/`, run `grep -nE 'json\.NewDecoder\(r\.Body\)' backend/internal/api/handler/*.go`. Every hit that isn't `decodeJSON` is a regression. Consider adding a small `staticcheck` analyzer or a `go test` linter that fails CI on direct `json.NewDecoder(r.Body)` outside of `health.go`.
