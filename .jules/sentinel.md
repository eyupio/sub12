## 2026-06-18 - Uncapped ?limit= on Ten List Endpoints (incl. unauth public leaderboard)
**Vulnerability:** Ten list handlers across `backend/internal/api/handler/` (`notification.go`, `user.go`, `event_invitation.go`, `feature_request.go` ×2, `support_ticket.go` ×2, `report.go`, `pellet_testing.go` ×2) parsed `?limit=` inline with their own little block — accepting any positive int with no upper bound. The worst case was `pellet_testing.go` `PublicLeaderboard` because it's the only public, unauthenticated route in the group: `GET /api/v1/pellet-tests/public-leaderboard?limit=999999999` would stream the entire leaderboard table out of the database. The repo already exposed a tested `parsePagination(r, defaultLimit, maxLimit)` helper in `health.go:59` that was used by ~10 OTHER handlers correctly.
**Learning:** A canonical helper only reduces risk if the *only* path to read pagination params is through it. New code drifted to copy-pasting the inline pattern because each block was 4 lines and "looked obviously fine." The same lesson as the journal's earlier 2FA decodeJSON entry — a helper exists, but discipline is fragile and grep is your friend.
**Prevention:** Grep with `Get\(\"limit\"\)` in `backend/internal/api/handler/`. Every hit that isn't inside `parsePagination` is a regression candidate. The new `TestParsePagination_LimitClampAndOffset` table-test in `pagination_test.go` pins the helper's contract (limit clamps to maxLimit, offset >=0, non-numeric → defaults). Consider extending the CI vet step with a `go test`-style linter that flags `Get(\"limit\")` outside the helper.

## 2026-06-11 - Unbounded JSON Body Decode on 2FA Handlers
**Vulnerability:** `backend/internal/api/handler/two_factor.go` called `json.NewDecoder(r.Body).Decode(&body)` directly in three handlers (`EnrollConfirm`, `Disable`, `RegenerateBackupCodes`). The package already exposes `decodeJSON(r, v)` (in `health.go`) which wraps the body in `io.LimitReader(r.Body, 1<<20)`, but these handlers bypassed it. A streaming POST could exhaust memory on the host since `json.Decode` keeps growing internal buffers until EOF or top-level value parses.
**Learning:** The repo already enforces a body cap at the public-auth boundary (see `security(auth): cap public auth endpoint bodies at 1 MiB`), and the `decodeJSON` helper exists exactly for this purpose, but newer handlers reached for `encoding/json` directly because the `auth.go` body-cap was wired via a different helper. A single canonical decoder is only useful if it is the *only* path to read JSON.
**Prevention:** After any change in `backend/internal/api/handler/`, run `grep -nE 'json\.NewDecoder\(r\.Body\)' backend/internal/api/handler/*.go`. Every hit that isn't `decodeJSON` is a regression. Consider adding a small `staticcheck` analyzer or a `go test` linter that fails CI on direct `json.NewDecoder(r.Body)` outside of `health.go`.
