## 2026-09-24 - `grep -rn "confirm("` closed one class of missing-confirmation bug, not all of it — a second class fires the mutation directly, with no dialog and no native `confirm()` either
**Learning:** The 2026-07-xx entries below closed every native-`confirm()` call site in `pages/` and concluded the cleanup item was done. But `AdminClubDetail.tsx` and `AdminLeagueDetail.tsx`'s "remove member" trash-can buttons had a worse variant of the same bug that `confirm(` can never match: `onClick={() => removeMemberMutation.mutate(m.user_id)}` fired the destructive request on the very first click, no browser dialog, no branded one, nothing — a misclick just removed someone's membership and any moderator permissions. Both files already import/render a `ConfirmDeleteModal` for their own "Delete Club"/"Delete League" danger-zone button a few lines below, so the inconsistency was easy to miss by reading either action in isolation. Fixed by holding the target member (`{ id, name }`) in state and gating the mutation behind the shared `ConfirmDialog`, clearing state via `onSettled` (not `onConfirm`) so the dialog also closes on a failed request — same precedent as the AdminEvents/AdminBackup entries below.
**Action:** To find this class of bug, grep `onClick={() => .*Mutation.mutate(` in `pages/` and check each match for a destructive-sounding mutation name (`delete`, `remove`, `revoke`, `block`, …) that isn't already gated by a `disabled={...confirm text !== 'DELETE'...}` typed-confirmation field, an inline `confirming` step, or a dialog wrapping the click. I checked the other `deleteMutation.mutate()` call sites this same grep turned up (`PrivacyCenter.tsx`, `Profile.tsx` account deletion, `AdminSupportTicketDetail.tsx`) — all three were already safe (type-to-confirm or inline confirm-step patterns) — and `removeMemberMutation.mutate(` had exactly these two hits, both fixed. Worth re-running this broader grep in a future session rather than trusting the narrower `confirm(` one to mean "no missing confirmations left".

## 2026-09-17 - Two identical local `Field` helpers had a sibling label with no `htmlFor`
**Learning:** `QuickCapture.tsx` and `Gear.tsx` each define their own local `Field({ label, children })` component (copy-pasted, not shared) used to wrap every plain rifle/pellet form input. Both rendered `<label>{label}</label>` as a sibling div-child of the input rather than an associated label — the input's accessible name fell back to its `placeholder`, which vanishes once typed. Since `children` is an arbitrary `ReactNode` (no `id` to reference), the fix was to make the `<label>` the wrapping element around `children` instead of a sibling — implicit label association, no id threading needed, and safe here because every `<Field>` call site wraps exactly one plain `<input>` (checked both files first: `CatalogSearch`, which already has its own `aria-label`, is always used standalone, never inside `Field`).
**Action:** When a codebase has more than one local helper component with the same name in different files, check both for the same bug — they're usually copy-pasted from a shared origin and drift together. Before wrapping arbitrary `children` in a `<label>` for implicit association, confirm every call site's children is a single plain form control; a multi-control child (like a combobox with its own labelled input) would get a confusing accessible name if wrapped this way.

## 2026-08-20 - ImageModal was the one dialog missing the codebase's own focus-management pattern
**Learning:** Every dialog in `components/` (`FlagDialog`, `ReportDialog`, `PersonaEditDialog`, `SubmitToEventDialog`, `SubmitToLeagueDialog`, `MapLocationPicker`, `ShareDialog`, `ConfirmDialog`) shares one hand-written pattern: on open, save `document.activeElement` into a ref and move focus to a control inside the dialog; on close, restore focus to the saved element; and a keydown listener that both closes on Escape and traps Tab/Shift+Tab between the dialog's first and last focusable nodes. `ImageModal` — the full-screen photo viewer used from `Feed.tsx` and `CommunityReview.tsx` — only had the Escape half. It's rendered conditionally with no `open` prop (`{zoom && <ImageModal .../>}`), so a keyboard/screen-reader user opening it landed with focus wherever it already was (often nowhere useful, since the trigger is usually an `<img onClick>` with no natural tab stop), could Tab straight through the modal into the page behind the black overlay, and on close focus wasn't restored to what opened it. Fixed by copying the exact pattern from `FlagDialog`, adapted for no `open` prop: the activeElement-save/restore effect runs on mount/unmount (empty deps) instead of gating on `open`, since mounting *is* opening here.
**Action:** When a component in this codebase is a modal/dialog (`role="dialog"` or `role="alertdialog"`), check it has all three: initial-focus-on-open, Tab-trap, and restore-focus-on-close — not just an Escape listener. `PickerModal.tsx` (used by `CardContextPicker`) is the other outlier: it has Escape-to-close but no focus trap or initial/return focus, worth fixing in a future session using the same pattern.

## 2026-05-27 - Comment input: placeholder ≠ label, silent maxLength is invisible
**Learning:** This codebase has excellent ARIA hygiene on buttons (aria-label on every icon-only button, aria-pressed, aria-expanded, aria-haspopup) but the inline comment `<input>` inside `PostCard` relied solely on `placeholder` — no `aria-label`. The pattern recurs wherever a text input appears *inside a form that already has a labelled submit button*; devs may assume the button context implies the input's purpose, but screen readers don't share that assumption. Also: `maxLength` on an input is completely invisible to users — the browser just silently stops accepting characters. Always pair `maxLength` with a visible counter (show when < 80 remaining, turn red at < 10).
**Action:** When reviewing inline comment/reply boxes in this app, check for (1) `aria-label` on the `<input>`, and (2) a visible `"{n} remaining"` counter linked via `aria-describedby` + `aria-live="polite"`.

## 2026-05-27 - CatalogSearch: custom comboboxes need explicit ARIA even when keyboard-navigable
**Learning:** `CatalogSearch` (used in the pellet and rifle wizards) had working keyboard navigation (arrow keys, Enter, Escape) but was completely silent for screen readers. The component had no `role="combobox"`, no `aria-expanded`, no `role="listbox"` on the dropdown, and no `role="option"` on suggestions. Crucially, the accessible name of the input was only the `placeholder`, which vanishes the moment typing begins — so the input became a completely anonymous text field mid-session. The fix combined `type="search"` + `aria-label={placeholder}` + full combobox ARIA (role, aria-expanded, aria-controls, aria-haspopup, aria-autocomplete) + `role="listbox"` + `role="option"` / `aria-selected` on each item. React 18's `useId()` pairs the input to its listbox id reliably even when multiple CatalogSearch instances are mounted simultaneously.
**Action:** When reviewing wizard steps in this app, check every custom dropdown/autocomplete for: (1) `role="combobox"` + `aria-expanded` + `aria-haspopup="listbox"` on the input, (2) `aria-label` (not just placeholder) on the input, (3) `role="listbox"` on the container, (4) `role="option"` + `aria-selected` on each item. Visual keyboard navigation alone is not sufficient ARIA coverage.

## 2026-07-16 - AdminBackup.tsx converted; native confirm() fully eliminated from pages/
**Learning:** Finished the last file from the entries above. `AdminBackup.tsx` had 3 destructive-action call sites (restore run, delete run, upload-and-restore) but they're mutually exclusive in the UI — never more than one pending confirmation at a time — so a single discriminated-union state (`ConfirmAction = { type: 'restore' | 'delete' | 'upload-restore'; ... }`) plus one shared `ConfirmDialog` instance covered all three without duplicating dialog JSX per action, keeping the diff small. Each of the three mutations already had distinct `onSuccess`/`onError` side effects, so `onSettled: () => setConfirmAction(null)` was added to each (not a single shared callback) — matches the `AdminEvents.tsx` precedent of clearing state via mutation lifecycle rather than the dialog's `onConfirm`, so the dialog closes on error too.
**Action:** `grep -rn "confirm(" frontend/src/pages` (excluding `confirmMutation`/`*Api.confirm(` false positives) now returns zero native browser-dialog call sites — this recurring cleanup item is closed. Future sessions adding a new destructive action should reach for `ConfirmDialog` from the start; if 2+ destructive actions live on the same page/modal and are mutually exclusive, prefer one shared discriminated-union state + one dialog instance over per-action state vars.
